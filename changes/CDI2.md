### Security
- **What the `Makefile` runs by sudo on Imladris, and what decides which host key ssh trusts, lives in scripts the code owners hold; the targets only call them** (CDI2, #922; the maintainer's decision of 19/11; `infra/glorfindel-host/README.md`, « Le CD d'Imladris »; `docs/design/modele-de-menace.md`, §7). After CDI1 (the CD's installation), three groups of recipes still acted on Imladris from the `Makefile`, which `.github/CODEOWNERS` does not own: a change there could change what sudo runs on Imladris, or turn off the check of its host key, without a code owner's approval. `make imladris-cd-enable`, `-cd-disable` and `-cd-uninstall` (the CD's timer turned on or off, the CD removed, by sudo in a terminal) now call `infra/glorfindel-host/cd/sudo_from_workstation.sh`, the same gesture each, to the byte, and the `Makefile` writes no sudo toward Imladris any more. The host key's check, `infra/glorfindel-host/known_host.sh`, is owned, `make imladris-known` only its call, and it also refuses, before reading the host's key, a `known_hosts` that is not a dedicated file (`/dev/null`, the account's `~/.ssh/known_hosts`, the system's). The SSH options of every target toward Imladris (`HOST_SSH_OPTS`) are printed by `infra/glorfindel-host/ssh_opts.sh`, owned, the same bytes as before (but for a `~` in `HOST_SSH_KEY`, which the three sudo recipes now pass to ssh as it is, and which ssh expands itself); when it prints nothing, `make` stops — never an ssh without them. Each owned script that acts on Imladris (the installation's and the sudo recipes') checks what it is given itself (`ssh_opts.sh check`) instead of believing the `Makefile`: the address, the user, the pinned form word for word, and the `known_hosts` it names — a file, not empty, neither the account's nor the system's, holding the key of that address. Nothing changes for the maintainer: the same targets, the same output; a missing VM is now also said by the three sudo targets (« Pas de VM : make imladris-up d'abord ») instead of ssh's error. What stays, assumed: a hostile `Makefile` may no longer call these scripts and run its own ssh; the other recipes toward Imladris run through `HOST_SSH`, their commands written in the `Makefile`, as the VM's user — a member of the `docker` group, as good as root, and probably given a passwordless sudo by cloud-init (not measured): no sudo is written in the `Makefile`, but a `docker` command can do as much; this lot closes the written sudo and the key's pinning, not that way. Orodruin's SSH options (`SSH_OPTS`) also stay in the `Makefile`, with no owned script; only `orodruin-known` goes through `known_host.sh`. Assumed for the same reason: the maintainer runs these recipes on his workstation, with his rights, and reads what he runs.
  - Tests: `tests/unit/test_host_ssh_owned.py` runs the targets against a fake `ssh` and a fake `ssh-keyscan` that note each argument, and keeps them to the byte (what the recipes sent before, measured against them), the refusals of weakened options before any call (`StrictHostKeyChecking=no` or `accept-new`, `UserKnownHostsFile=/dev/null`, an empty `known_hosts`, the account's, one without Imladris's key, `-F`, `ProxyCommand`), sudo in the owned script alone, and `make` stopping when the options are not printed; `tests/unit/test_codeowners.py` derives the scripts from the `Makefile`'s rules and requires their line (mutants M6571–M6585, `scripts/mutants/CDI2.py`; CDI1's M6359, M6361–M6365, M6381–M6383, SEC-C's M5461 and SEC7's M1420 re-anchored to `ssh_opts.sh`, where their lines moved).
