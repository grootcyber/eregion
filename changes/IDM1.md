### Added
- **The identity map: who holds what, from where, under which identity — Azure, Entra ID, GitHub, Discord, the workstation, the phone, Imladris (formerly H0) and Orodruin** (IDM1, #687 ; `docs/design/identites.md`, `scripts/identity_map.py`). Four mermaid diagrams (the network, the defence's identities, the red team's and the bench's, the workshop), each link saying what crosses it and under which identity. Every role read action by action, as its file grants it, not as the code uses it: Response can rewrite any network interface, NSG and rule of its resource group and attach any public IP there, so it can make a VM more reachable; Restore can rewrite any VM of its group (profile, attached disks, userData, system identity), any disk, and the configuration of any storage account (firewall, shared key, public access), which amounts to replacing a VM's OS disk; Session Drain and Restore Neutralize run any command as root on their VM. A matrix, one line per identity — 38, among them 4 planned (the Stratus identity of R2/R2c, the restore executor of FS1g, the TOTP secret of TOT1, the dedicated Graph identity of 0.6.2) —: where it lives, where its secret lives or that it has none, who uses it, its rights by kind of scope, what it cannot do, its rotation and expiry, the threat model's boundary that holds it, and whether the repository declares it, Eregion's code draws it, or it is made by hand. A register ties each declaration of the repository to its lines: every role of `infra/identities/`, every Terraform identity or right (role assignments, keyed by their role and the expression of their scope, so that a role or a scope changed is said; role definitions, user-assigned identities, key vault access policies, azapi role assignments, every `azuread_*` resource, every `identity`, `admin_ssh_key` and `access_policy` block, `dynamic` or not, in `.tf` and `.tf.json`), every identity variable of the compose and of the example environments, every secret, `secrets: inherit` and write permission of the workflows (`.yml` and `.yaml`). Every action of a role file or of a Terraform role definition, every Graph permission and every directory role must be named in the matrix. `python3 scripts/identity_map.py check` says what is missing, `list` what the repository declares. No real identifier: roles, kinds of scope, generic names. How `make bench-preflight` would compare the live assignments to the map is proposed as a follow-up (§5); what the check cannot see is said (§6). The threat model, `docs/architecture.md` and `docs/operations.md` (« Identités Azure ») point to it.
  - Tests : `tests/unit/test_identity_map.py` — the map holds every declaration; one added without its line fails (a role file, an assignment, a definition, an Entra ID resource, a user-assigned identity, a key vault access policy, an azapi role assignment, a `.tf.json` assignment, a managed identity on a resource — nested, `dynamic` —, an SSH key, a pair in the compose, a token, a key, a password, a SAS, a connection string, a fingerprint, a certificate, a commented pair, a workflow's secret in either form, `secrets: inherit`, a `.yaml` workflow, a job's OIDC token, a top write permission); an assignment's role or scope changed, an action added to a role file or a Terraform role definition, a Graph permission or a directory role not named in the matrix, a stale row, an unknown line, a « dépôt » line nothing feeds, a planned line already declared, a missing column or boundary, a role not named on its lines fail.
