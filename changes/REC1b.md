### Fixed
- **The watch decides a neutralization by the control plane alone, and the platform's refusals hold nothing** (REC1b, #679; `docs/glorfindel.md`, « La reprise lue sur Azure »). On the bench (09/11) the instance view never carries Run Command v1: `RunCommandLinux` is `Ready` in `vmAgent.extensionHandlers` but absent from `instanceView.extensions`, before a restore, after it, and after a replayed neutralization. REC1's watch waited 15 min for that word, never found it, and held every release with a card, so the loop never closed with the restore alone.
  - The activity log decides: the last succeeded Run Command before the job came from a principal that restores, after the isolation, and none from another principal since. The guest's word is now information only. Its absence holds nothing, and the watch no longer waits for it (`GLORFINDEL_RECOVERY_REPLAY_WAIT_S` is gone). If it is present, dated after the job, and is anything but the harmless output, it contradicts the control plane and the release is held.
  - **A Run Command refused by the platform is not counted, whoever ran it**: an event `Failed` with HTTP status `Conflict` and error code `OperationNotAllowed`. This was measured on a deallocated VM: the command never reached the guest and left the VM model as it was. The adapter reads the status in `properties.statusCode`, else `subStatus`, and the code in the top-level error of `properties.statusMessage`. Each refusal takes with it one `Started` at most: the closest before it, of the same operation (`operationId`), by the same caller, at most 60 s earlier (about 2 s on the bench). A `Started` left over, or outside that window, still holds the release: where `operationId` comes from is unmeasured, and an id a client could choose would otherwise let a command cut by the deallocation hide behind a later refusal. Any other failure of another principal still holds the release (REC1's rule m1): another code, another status, a code under `details`, or a message that is unreadable or missing. The query now selects `subStatus`, `properties` and `operationId`. Where exactly ARM writes that status and that code is unmeasured. If they are missing, a refusal reads as another failure, and the release is held.
  - Measured and now written in the docs: the activity log names a principal with a secret the same way as a managed identity (`caller` and `claims.oid` = object id, `claims.appid` = appId), and a restore in place has the « Job Type » « Replace disks ». The operator's rule (`docs/banc-t1486.md`, `docs/design/modele-de-menace.md`): an integrity read by Run Command comes after the release, or runs under a principal that restores. Run before the release by anyone else, it holds the automatic release.
  - Tests: `tests/unit/test_recovery_watch.py`. A view without Run Command and a control plane that proves the neutralization lifts once. Refusals from the restoring principal and from others hold nothing. Six other failures from another principal hold the release. The bench's activity log of 09/11 lifts with the restore alone. Two `Started` for one refusal, or one ten minutes before it, hold the release. `tests/unit/fake_azure.py` changes: the instance view carries no Run Command by default (`view_run_command`), a Run Command on a VM that does not run is refused and logged, and each operation gets its own id. The state machine draws the view, the deallocation before the restore, refusals from each principal and a contrary word. Mutants M4650–M4653 (`scripts/mutants/REC1b.py`).
