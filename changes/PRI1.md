### Added
- **Design, settled: a classification of the VMs, for the model's cost and the order of its queues only** (PRI1, #1216; `docs/design/classification.md`, `docs/design/configuration-console.md` §3.3). Today a VM has one yes or no, `critical: true` on an entry of `autonomy.assets` (PRT2): its grave detections keep part of the model budget's reserve and never wait for the provider's cool-down. The maintainer answered the note's ten questions on 26/11 and set its frame: the classification serves the management of costs, an order of priority in the queues, and changes nothing of what Glorfindel detects or how it responds — with one exception, said as such: an exhausted model budget, which changes what Glorfindel does exactly as an exhausted budget does today (an ordinary detection becomes a card, a grave one takes the code's path). A VM's class is the operator's declaration, in the configuration file alone, in three levels that do not alarm: `essential` (today's `critical: true`), `standard` (the default) and `quiet`. It sets the model's reserve and budget, the order of the grave calls to the model waiting for room (an order between the VMs the gate does not have today, to add; a grave detection is never starved, a low one never waits), and what the console shows. With a tight budget, an essential VM's grave detection keeps the model where a standard one takes the code's path, as today. A smaller budget for a quiet VM's ordinary detections (a quarter, proposed) would send them to a human beyond it: an open question, asked of the maintainer on 26/11. It touches neither the rules, the enquiry, the dossier, the cards, the notifications, the mode nor any guard: an essential VM's mode is shown beside its level (`ESSENTIAL · NON_DISRUPTIVE`), never corrected. The note inventories every reader of `critical` in the code and states four findings, among them that setting it forces a mode on the entry and can be classed as a relaxation, and that the push to the hosted watch copies any section other than the autonomy as it is. The format, the maintainer's own proposal: one `assets:` section replaces `autonomy:`, with `default_mode`, `allow_destructive` and a `list` of entries carrying an optional `mode` and an optional `priority`, each resolved by the exact entry, then the longest pattern, so `standard` is a level like the others and a descent is a relaxation; the discovery stays on its source. The former format (`autonomy:`, and `critical: true` read as `essential`) is read until 1.0 with a note inviting to migrate, by a command whose migration is classed neutral; both formats in one file are a configuration error. The watch's reading and the push's change together and are held equal by a test; the push never lowers the level Imladris gives to any name or pattern, writes the format the hosted watch's release reads, and migrates a hosted watch still on `autonomy:`. A new rule for the whole file, to be built with CFG5: when the watch reads the file again, a hand edit included, what tightens applies at once and what relaxes is held, the former value kept, until a human confirms it; it replaces the decision of 23/11 that a hand edit was announced, then applied; a lost record of the applied configuration falls back to the prudent default, said loudly, and a confirmation typed at the CLI on the host applies without the delay. Four lots in 0.6.x (PRI2a, the format and the migration; PRI2b, the push and its version guard; CRT1, the display; PRI4, the order between the VMs and the quiet VMs' budget), PRT3 in 0.7, the former format removed at 1.0. What the model sees does not change. No code changes.
