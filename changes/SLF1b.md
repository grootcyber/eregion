### Fixed
- **The watch's own return channel is set aside again in production: the query's writers are read as the SDK hands them on, as JSON text** (SLF1b, #976; `docs/glorfindel.md`, « La voie de retour de la watch »; `docs/azure.md`). Since 0.6.2 was deployed on Imladris, the watch's heartbeat (three writes of `heartbeat.json` by its identity, in its container) still made an unattributed `data-exfiltration-blob` card every 10 minutes, the rule's `own_channel` counter empty: `azure-monitor-query` hands a `dynamic` column on as the text the API sent, and `own_channel.settle` kept any row whose `BlobWriters` was not a Python list — the form SLF1's tests passed. The column is now read as a list or as a JSON text of at most 64 Ki characters (65,536) that decodes to a list of objects (`own_channel.writers_of`); every other condition of SLF1 is unchanged (the account, the container, the writer, every write a channel's object, the shipped rule only). A text unreadable, nested too deep, longer than the bound, or that is not a list of objects sets nothing aside — the row stays a card, its counts whole —, never raises, and is said: counted beside `own_channel` in the rule's status (`unparsed`, `unparsed_last`), in the watch's log, and in the rule's details in the console. The other reader of a `dynamic` column a shipped rule returns (auditd's `Syscall` and `Execve`) already read both forms; it is now proven on the SDK's objects too. No shipped query changes, nor what the model reads.
