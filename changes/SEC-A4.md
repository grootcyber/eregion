### Security
- **A detection row is never attributed by its host name: a rule whose rows carry neither `_ResourceId` nor `CallerIpAddress` is refused at load and at approval** (SEC-A4, #633; audit of 06/11, V-04; `docs/glorfindel.md`, « L'attribution d'une ligne »). A row without `_ResourceId` was routed by its `Computer`, which root on the VM chooses: a rule without it — a rule proposed by the model and approved, for one — made the watch isolate or block in another VM's name, and the two-homonyms guard only held between two passes of the discovery (every 30 min). `RowAttribution` no longer reads `Computer`: a row is routed by the resource Azure writes (`_ResourceId`, or `ResourceId`) or by the private address that made a call (`CallerIpAddress`); a row that carries only its host name is unattributed (an anchored card, the actions held). At load, in any layer (the base, the client's layer, hence the approved rules), a rule of the data plane whose query keeps neither key is refused and said; a refused copy in the client's layer leaves the shipped rule of its name. `glorfindel approve-rule` and the console refuse it with the reason, the proposal kept pending, nothing written. The query is read on its text (`eregion_core/rule_routing.py`), the strictest reading, which refuses at the slightest doubt rather than follow a value: a key is kept only while it holds what Azure wrote — a table carries `_ResourceId`, a storage table (`StorageBlobLogs`, `StorageFileLogs`, `StorageQueueLogs`, `StorageTableLogs`) carries `CallerIpAddress` too, a `union` what all its members carry; `project`, `distinct`, `summarize … by`, `arg_max`/`arg_min` keep a key only if they name it and it is still there; `project-away`, `project-keep`, `project-rename` drop it. A query that writes a routing key anywhere, in any case, is refused, whatever it writes from (`extend`, `project X = …`, `project-rename`, `summarize X = …`, a named output of `arg_*`, `parse … with … X:string`, `print`, `datatable`, a `let`) — but one rewrite, read as none: the port taken off the storage caller's address, exactly `CallerIpAddress = tostring(split(CallerIpAddress, ":")[0])` (`data-exfiltration-blob`). An assignment of a form it does not read (a bracketed name, a tuple, a top-level `=` whose left is not a bare name), an unknown operator, a source it cannot read (`datatable`, `print`, `evaluate`, `union withsource=`), a string not closed: refused, never assumed. `CallerIpAddress` on any other table — a custom table fed from the VM, root's word — is refused. The control plane and identities, filed on what their rows name (AL1c), are not concerned. Every shipped rule is conformant and none changes: the eight rules of the data plane keep `_ResourceId`, `data-exfiltration-blob` is routed by `CallerIpAddress`. The analysis AI's triage (`analysis/triage.py`) reads the same refusals.
  - Tests: `tests/unit/test_rule_routing.py`, `tests/unit/test_analysis_rules_parity.py`, `tests/unit/test_detection_rules.py`, `tests/unit/test_unexpected_decision.py`; mutants M4541–M4543, M4600–M4604 on the reader (M1335 and M1363, the host name's reading, retired). A limit to measure on the bench: a row with an empty `_ResourceId` is no longer attributed by its host name — its isolation held, what the model reads changed.
- **A call made from an appliance's address is never pinned on the appliance: every action is held, and the card says the source is behind it** (SEC-A4, #633; audit of 06/11, V-05; `docs/glorfindel.md`, « L'attribution d'une ligne »). Behind a network appliance that SNATs toward a private endpoint (required when a third-party appliance inspects that traffic), the storage service sees the appliance's address: `data-exfiltration-blob` attributed the exfiltration to the appliance, and the card proposed — in `non_disruptive`, ran — the isolation of a whole hub, the VM that exfiltrates untouched. `private_ip_owners` now reads `enable_ip_forwarding` on each network interface: every address of a VM one of whose NICs forwards packets is marked. A row from such an address is unattributed (`attribution_via: appliance`), its card anchored on the appliance when the rule watches it, and `decide`'s attribution guard holds every action — the isolation, the block, the snapshot, the release —, whatever the model or an earlier gate said; the card says the source VM is behind the appliance, to be found in its logs. The same reading for an `attack_started` and for a card of the control plane; a rule bound to one asset never takes such a row for its own. Limits, in the documentation: the source VM is not found (no source reads an appliance's logs yet), an explicit proxy without IP forwarding is not recognised.
  - Tests: `tests/unit/test_rule_routing.py` (the in-memory Azure of the invariants, `tests/unit/fake_azure.py`, now carries `enable_ip_forwarding`); mutants M4540, M4544.
