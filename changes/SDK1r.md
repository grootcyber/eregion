### Added
- **Annatar's Log Analytics collector is now read through the pinned SDK's own objects** (SDK1r, part of #992; `annatar/collectors/azure_monitor.py`, `tests/unit/test_annatar_collector_sdk.py`). The Glorfindel side of SDK1a (#1001) moved its Log Analytics readers onto the pinned `azure-monitor-query` SDK's `LogsQueryResult` through the shared `tests/unit/sdk_logs.py`; this does the same for Annatar's own collector. `AzureMonitorCollector` — which polls Log Analytics for the VM's heartbeat after a restore and for an attack's alert — had no test at all. It is now driven through the real `LogsQueryClient` over sdk_logs' in-memory transport (no network, a made-up token): a reply is built as the service sends it, and the collector reads it as a `LogsQueryResult`.
  - `AzureMonitorCollector.__init__` takes an optional `client=`, so a test injects the SDK client built over the test transport (the seam the collector lacked); production still builds its own from `DefaultAzureCredential`.
  - Tests: the heartbeat poll returns on a real datetime row and times out on none or on a null `LastHeartbeat` (the empty summary is not a pulse); the alert poll returns on rows, times out on an empty table, and refuses an unknown source. D1 holds — the test uses only sdk_logs' `.client()` brick (the raw SDK client), never `.detector()` / `.serve()` / `through_sdk()` (Glorfindel's side), so the Annatar component still runs alone with Glorfindel absent (`scripts/component_check.py annatar`). Mutants M6826–M6830 (`scripts/mutants/SDK1r.py`).
