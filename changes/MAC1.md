### Fixed
- **A release refused at the VM's lock during a race is no longer read as a release under way by the invariant machine** (MAC1, #1178; `docs/design/preuves.md`). The night « Invariants (deep) » of 24/11 was red on macOS only (seed 397333194): « I9: the reassertion isolated …/batch again mid-release ». Every draw replays the same on Linux; what differs is the order a directory is listed in. The reassertion reads the blocks in `Path.glob`'s order, and APFS lists a directory by a hash of each name (the CRC-32C of its normalized form), not by name. In that order, the reassertion held the lock of two VMs of the same name in a row; the release of one waited its bounded turn, gave up and wrote nothing, the VM still isolated whole. The machine's journal had marked that release under way and ended it only on « released », so the isolation the reassertion then rightly put back read as undoing a release. The oracle's, not the product's: as for a release alone, a lift that failed before writing anything to Azure started nothing, judged by the fake's journal of who wrote, by thread (the AWS world's too, by symmetry). The product is unchanged.
  - Tests: `tests/unit/test_invariant_regressions.py` replays the sequence, reduced from 15 rules to 6, with every directory listed in APFS's order (`apfs_listing_order`), so the ubuntu CI keeps it: red on `main` with the night's message, green with the fix; the journal's rule alone, on five cases, a write by a thread of neither operation keeping every VM under way. Mutants M7576–M7577 (`scripts/mutants/MAC1.py`): a writer refused at the VM's lock goes on without it; that safe way taken out.
