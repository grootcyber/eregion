### Security
- **Glorfindel's rules, local state and restore records belong to a VM by its full identifier** (SEC-H, #849; `docs/azure.md`, « Les noms par l'identifiant complet » ; `docs/fichiers-cles.md` ; `docs/glorfindel.md`, the recovery read on Azure ; `docs/design/modele-de-menace.md`, the decisions assumed). Two VMs of one name, whose NICs are named alike, no longer share a rule, a state file, an original or a restore.
  - The isolation and block rules end with 128 bits of the NIC's id (SHA-256), at most 80 characters with `-out`. The names an earlier version wrote are read, never trusted on the name alone: a rule under one of them is a NIC's when its VM's state records it, or when it is a deny that applies to the NIC's addresses; what was placed before the upgrade is verified under its old names, lifted through its state, and written again under the new ones. On an NSG the NIC does not carry — the one a bare NIC left, any NSG for a deleted VM — two VMs of two VNets often hold the same private address: an older name there is the NIC's only when its VM's state records it on that NSG, or as a deny of the NIC's addresses that covers no other live NIC that NSG governs; anything else is left and said, never a release done, and a homonym's deny never lost. A prefix too long even for the VM's name (an IPv6 block) keeps 64 bits of the address's hash: one name per address. The orphan sweep reads both marks.
  - The key of a NIC's original on the shared quarantine NSG holds 128 bits too; the earlier key is read, never written again. A tag names an original only when it is an NSG of the subscription Glorfindel acts in, never one of its quarantine NSGs. A bare NIC's original is read on the quarantine NSG of the configured group only: one of another group that names an original holds the NIC as it is and says so, until the operator writes the original on Glorfindel's tag; met at a re-isolation, the reason is kept on the placement and said again at the release, that NSG named.
  - A state file is a VM's only when the resource id it records is: two VMs whose 8-hex keys meet keep two files. An unreadable block file is set aside before a new block, as the isolation state is, and lifting one address's block no longer deletes the other addresses' entries.
  - The restore jobs, the last restore and the restore claim are keyed by the VM's full id; the vault's job is chosen by its container too. The model's message reads the last restore as before: for a VM without a homonym, byte for byte the same.
  - The recovery read takes who ran a Run Command by object id only — an application's token by its object id, a user's delegated token never by the application it signed in through; `GLORFINDEL_RESTORE_PRINCIPALS` takes object ids only, and an appId found there is said on the card. Its next pages stay on Azure Resource Manager.
  - The ARM writes of the isolation and the block are waited for a bounded time (`GLORFINDEL_ARM_WRITE_TIMEOUT_S`, 300 s), a writer behind a VM's lock too (`GLORFINDEL_VM_LOCK_WAIT_S`, 900 s); the reassertion says every VM it skips, on a card from the fifth pass in a row (`GLORFINDEL_REASSERT_SKIPS_SAID`).
  - Tests: `tests/unit/test_wide_marks.py`, `tests/unit/test_full_id_keys.py`, the invariant machine (an isolation and a block under the earlier names); mutants M5801–M5820, M5941–M5945 and M6221–M6225 (`scripts/mutants/SEC-H.py`).
