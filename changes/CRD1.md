### Fixed
- **An unusual sign-in of a service principal now proposes to remove the one credential it used, not only to disable the whole principal** (CRD1, #1011; `docs/glorfindel.md`, « La connexion inhabituelle retire l'identifiant qu'elle a utilisé » ; `docs/design/reponse-identite.md`, hypothesis 7). Measured on the bench on 21/11 (E7 of ID1): `AADServicePrincipalSignInLogs.ServicePrincipalCredentialKeyId` names the credential a sign-in used, on 5 sign-ins out of 5 (`clientAssertion`), and its value is the certificate's `keyId`. Hypothesis 7 of the design holds. But the shipped rule `entra-sp-unusual-signin` did not keep that column, so the card's plan always proposed `entra_disable_principal`: all the principal's legitimate use stopped with it.
  - The query now keeps the credentials of each group's sign-ins (principal and address): `CredentialKeyIds = make_set(ServicePrincipalCredentialKeyId, 5)`, projected under that name, the only one the plan reads. The 14-day baseline (the last hour left out) and the thresholds are unchanged.
  - The column arrives as `dynamic`, so as its JSON text (SLF1b): `entra_items.used_credential` reads it through `own_channel.json_of`, bounded, never raising. A single `keyId` (a GUID): the plan proposes `entra_remove_credential` on it, and the principal's other credentials stay. If Graph is read and neither the application nor the principal carries that `keyId`, the plan proposes `entra_disable_principal` instead: a federated sign-in names a `keyId` that is no credential of the application (measured on the canary, 11/11), or the credential is already removed. If Graph is not read, the log's `keyId` is still proposed, its object said not read, as before. Several (an empty value counts: a sign-in that named none), none, a value that is no GUID, an illegible text, or the column absent: `entra_disable_principal`, as before, with the reason said in the step. Nothing runs alone: it is a plan proposed to a human.
  - The step that disables a principal now reads « Bloquer la connexion du principal de service » (E-6).
  - The rule's fingerprint changes. A copy of this rule in a customer's layer taken before CRD1 is set aside (WL1, its drift said), and the shipped rule runs in its place. The bench's copy (CAN3, `infra/glorfindel-host/client_rules.bench.yaml`) is redone in the repository and reaches Imladris by `make imladris-client-rules`; until then the shipped rule runs there, and the canary's cards come back.
  - To confirm on the bench: `make_set` keeps the empty value of a sign-in that names no credential. Otherwise a group that mixes both would show only the named credential.
