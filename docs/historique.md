## Boucle purple team — implémentée

**Détection manquée (réactif) :**
```
Annatar attaque → detection_timeout
  → thread daemon (_wait_and_emit_feedback) poll runs/<run_id>_debug.jsonl
  → émet detection_missed {TTP, detection.hints, failed_query, source}
  → Glorfindel: propose_detection_rule node
  → 2 gates AVANT l'autoring (déterministes, zéro LLM) :
      (a) RulePoller a matché ce TTP récemment → faux négatif du watcher Annatar → skip
      (b) une règle couvre DÉJÀ ce TTP (detection_rules.yaml) → PAS de proposition :
          le raté n'est pas un manque de règle mais une détection EMPÊCHÉE
          (isolation résiduelle qui coupe l'AMA/l'egress, latence d'ingestion, backend KO)
          → escalade `detection_blocked` (action `investigate_detection_gap`) qui pointe
            posture/latence/backend. Constat 1er run e2e campagne (20260730T193824Z) :
            2 ratés d'origine infra → 2 règles doublon autorées (T1110, T1041) = bruit.
  → sinon (cold-start, TTP non couvert) → detection_authoring.author_rule (LLM grounded)
  → grounding : catalogue (table/colonnes) + getschema (schéma RÉEL du LAW au runtime)
  → ~/.glorfindel/proposed_rules.jsonl + escalation proposed_rule
  → glorfindel pending / War Room ⚙ → Approve
  → glorfindel approve-rule <id> → detection_rules.yaml
  → restart watch → règle active au prochain run
```

**Autoring proactif (cold-start) — `glorfindel propose-rules` :**
```
glorfindel propose-rules [--include-planned]
  → lit technique_catalog.yaml, skip les TTPs déjà couverts
  → pour chaque technique non couverte : getschema sur le vrai LAW → author_rule (LLM grounded)
  → propositions (pending / War Room) → approve-rule
  → génère la détection AVANT l'attaque (pas besoin d'un raté). Validé Azure réel (T1070.002).
```
**Deux couches anti-hallucination** : le catalogue (quelle table/colonnes) + getschema (colonnes
RÉELLES → le LLM n'invente pas de colonne). Invariant : sortie = proposition, RulePoller déterministe
inchangé, zéro LLM sur le hot-path. Le rejeu auto-activé en sandbox (étape 5) reste à venir (dépend
de l'exécuteur de campagne Annatar — voir collab/design_campaign_manifest.md).

**Remédiation non prête :**
```
glorfindel audit --all (ou watch startup)
  → AuditCheck par action: NSG (isolate_vm/block), backup (restore), compute (snapshot)
  → status: ok / warn (backup > 48h) / fail (IAM gap ou config manquante)
  → fix: commande az exacte pour corriger le trou
  → War Room ⚙ → section Remediation readiness par ressource
```

**Deux asymétries intentionnelles :**
- Réaction = LLM libre + RAG ChromaDB — apprentissage implicite, continu, aucune règle
- Détection = règles explicites (`detection_rules.yaml`) — source de vérité, query language = fonction du `source`.
  Les règles sont désormais **autorées par le LLM** (réactif sur raté + proactif `propose-rules`),
  groundées sur le catalogue + le schéma réel — mais restent des **propositions** ratifiées, exécutées
  par le `RulePoller` **déterministe**. Génératif à l'autoring, déterministe au runtime.
- Audit = vérification IAM + infra — détecte les trous *avant* l'incident

## Passes de revue et lots livrés

- **Troisième passe (07/10) — pas de succès sur une inconnue, bonne cible (L10, L11 en partie, L14 en partie)** :
  - `_original_from_tags` **lève** sur une erreur de lecture (avant : `None` → la levée laissait la carte **sans NSG** et `verify_release` disait vrai) ; la levée lit d'abord l'original dans l'état (`"original_nsg_id" in p`, `None` = la carte n'en avait pas), puis **relit la carte** (`_unquarantine`) : original absent ou inconnu → la carte reste en quarantaine, `release_partial`. Tags d'origine écrits sous verrou (`_quarantine_lock` : thread + flock `~/.glorfindel/locks/`) puis relus ; tag non posé → échange annulé, repli sur les règles. Ré-isolation d'une carte déjà en quarantaine : original repris de l'état (`_recorded_original`), pas écrasé par `None`.
  - NSG de quarantaine reconnu par son préfixe **et** son tag `managed-by: glorfindel` (`_managed_by_glorfindel` ; illisible → considéré comme le nôtre, la levée exige alors nos tags et échoue proprement) : un NSG client nommé comme les nôtres aurait été détaché par une levée sans état. Préséance au repos (`_precedence_issues`) : l'isolation est contrôlée sur **tout** NSG (L3 : première priorité libre dès 100).
  - `_rules_state` à trois états : une règle **illisible** n'est plus « disparue » → `verify_isolation` / `verify_block_ip` rendent `verified=None` (`unreadable_nics` / `unreadable_rules`), la réaffirmation ne repose rien. `_is_not_found` : 404 / `ResourceNotFoundError` seulement (la sous-chaîne « not found » couvrait aussi une ressource *référencée* manquante).
  - Coupure des sessions : `unsupported` (Windows) → **non vérifié** ; comptage `ss` en erreur → `failed` (avant : `| wc -l` donnait 0). Levée autonome seulement si `run_command_neutralized is True` (drapeau absent = inconnu → `release_hold`).
  - **Abonnement** : toute méthode d'action/vérification du connecteur refuse une VM d'un autre abonnement que `AZURE_SUBSCRIPTION_ID` (`WrongSubscriptionError` → `action_failed`) ; la préparation dit `other_subscription` (pas prête).
  - Règles : `ransomware-disk-write` lit la cadence de chaque série (`Step = min(Gap)`) — fine (≤ 25 s) : 2 échantillons > 45 Mo/s ; grossière (défaut Azure 60 s) : 1 échantillon > 25 Mo/s (moyennes 60 s reconstruites sur 10 jours : attaques 26,8–91,7, bénin max 23,2 — marge mince). **Mesuré le 07/10 avec la DCR du banc à 60 s** : T1486 de 50 s → échantillons 8,7 puis 42,2 Mo/s, détecté par le RulePoller à T0+~3,5 min (`isolate_vm` 82 % retenu par `human_only`) ; l'ancien seuil de 45 l'aurait raté. Le bénin reste mesuré sur moyennes simulées. `sudo-privilege-escalation` : `summarize arg_max(TimeGenerated, *) by Computer` au lieu de `| limit 1` (exécuté avant le filtre par VM → aveugle en multi-VM). Toute règle `assets: [auto]` avec `limit`/`take`/`top` → avertissement au chargement.

- **L24 (07/10) — invariants : sept défauts trouvés par les tests de propriétés, aucun par la revue** (`tests/unit/test_invariants.py`, réseau Azure en mémoire `fake_azure.py`) :
  - **Homonymes** : le nom de règle ne dépendait que du nom de la VM et de la carte. Deux `web` dans deux groupes, cartes `web-nic`, un NSG partagé (hub, « tier ») → isoler l'une réécrivait la règle de l'autre (rouverte), `verify_isolation` de l'autre répondait `True` sans avoir jamais été isolée, la réaffirmation rouvrait l'homonyme. Les noms portent désormais l'empreinte de l'ID de la carte (`glorfindel-iso-<vm>-<nic>-<h6>`, en minuscules ; l'ancien nom reste reconnu).
  - **Le nom n'est plus une preuve** : `verify_isolation`, `verify_release`, la levée et `reset --from-azure` lisent la liste des règles du NSG et ne comptent une règle comme celle de la carte que si c'est un deny qui s'applique à ses adresses (isolation : tous protocoles, tous ports, toute source, chacune de ses IP). Une seule lecture par NSG et par vérification.
  - **La levée balaie toujours** (`_sweep_isolation`) : après les placements de l'état, chaque carte est relue et ce que l'état ignore est retiré (crash entre Azure et le fichier d'état, réponse perdue après une écriture appliquée, placement remplacé). Avant : une ré-isolation interrompue réécrivait l'état avec la seule première carte, la levée disait `released` et la seconde restait isolée. Les placements précédents sont aussi gardés dans l'état (`_merge_isolation_placements`). Carte en quarantaine : relue après sa remise (son NSG d'origine, masqué, peut porter un ancien repli).
  - **Un deny de repli vise toujours les IP de la carte**, même sur un NSG qui semble dédié (`_scope_to_nic`, isolation et blocage) : une carte d'une autre VM partie en quarantaine n'apparaît plus sur son NSG, un NSG « tier » partagé semblait dédié, recevait un any/any, et l'autre VM se retrouvait coupée à sa propre levée.
  - **Subnet illisible ≠ subnet sans NSG** : `_subnet_nsg_of` lève sur une erreur de lecture ; la carte porte `subnet_unreadable` et levée, `verify_release`, `verify_isolation`, `reset --from-azure` le traitent comme une inconnue. Avant : un 429 sur cette lecture → levée sans état qui ne balayait rien et disait `released`.
  - **Une carte isolée par l'un de ses deux NSG** : un deny non contourné sur le NSG de la carte OU du subnet suffit ; la première paire trouvée décidait seule (un reste contourné l'emportait sur un deny sain).
  - `reset --from-azure` : une règle de la seconde carte vue au passage de la première était marquée « vue » puis ignorée — restait en place.
  - **Mesuré sur le banc (gondolin)** : quarantaine, repli sur les règles (NSG de subnet, règles `…-c271eb` en 100 visant 10.10.1.4), levée sans état — vérifiés (ID canonique et minuscules), levés, rien ne reste. Hypothèse non mesurée du faux : noms de règles insensibles à la casse côté Azure (le code n'en dépend plus).

Sur un NSG partagé, les refuser couperait toutes les VMs derrière lui. Le repli ne les pose donc pas et **le dit** : `platform_open` + note dans le résultat de l'isolation et dans la vérification (vraie, sans affirmation sur DNS/IMDS) ; préparation : `rules_fallback` le mentionne, nouvelle réserve `platform_open` quand la quarantaine est désactivée. Une première sonde par `getent` avait vu « ouvert » : le cache de systemd-resolved, rempli juste avant.

  - **Génération orientée** vers les états rares (composites : levée interrompue puis réaffirmation, isolation interrompue puis reprise, état et tags perdus puis ré-isolation et redéploiement, voisins isolés l'un après l'autre, blocage puis isolation). **Base Hypothesis** : la nuit l'enregistre (cache), chaque push la rejoue d'abord. Les séquences trouvées sont figées dans `tests/unit/test_invariant_regressions.py` (rejeu à la main, tirage par tirage).
  - **Cinq défauts trouvés et corrigés** :
    - **IP changée → règle de l'ancienne adresse laissée** : sans état, la levée et `reset --from-azure` ne retenaient une règle de la carte que si elle s'appliquait à ses adresses actuelles ; le deny de l'ancienne IP restait (`released`) et aurait coupé la prochaine VM à recevoir cette adresse. Un nom qui porte l'empreinte de la carte est à elle, quelle que soit l'adresse qu'il vise (`_nic_owns`, isolation et blocage) ; un nom ancien, partagé par les homonymes, doit toujours s'appliquer à ses adresses.
    - **`verify_block_ip` comparait aux IP enregistrées au blocage** : la carte changeait d'IP, « bloqué », la nouvelle adresse ouverte à l'attaquant. Relit les cartes (illisibles → `verified=None`, une règle absente reste un échec ; carte ajoutée depuis → manquante).
    - **Blocage caché derrière la quarantaine** : bloquer sur le NSG propre de la carte, puis isoler par quarantaine — ce NSG n'est plus sur la carte. NSG de quarantaine vidé → l'attaquant passe, et la vérification lisait les règles du blocage, présentes, comme un blocage. Ne comptent que les placements sur un NSG qui gouverne la carte **maintenant** ; la quarantaine, intacte, compte comme un blocage (sauf pour une source forensique).

Ce que fait la réaffirmation aujourd'hui, avec la ligne de code de chaque case, est dans la table de [`docs/design/reaffirmation.md`](design/reaffirmation.md), la référence depuis le 21/11 (Q1) ; son résumé, dans `docs/glorfindel.md`, « Réaffirmation »._

**La réaffirmation, écrite une fois (RSM1, #1018, 21/11)** : ce qu'elle repose, dit ou laisse, pour chaque objet posé (l'isolation par règles, la quarantaine, le blocage d'une VM, le blocage de périmètre) et chaque situation (intact, disparu, contourné, une levée en cours, une quarantaine qu'on ne sait pas juger, une lecture impossible, un NSG partagé ou détaché, une VM supprimée, une IP réattribuée), avec la ligne de code et l'invariant qui tient chaque case, puis les écarts entre le code et les oracles : [`docs/design/reaffirmation.md`](design/reaffirmation.md). Les paragraphes qui suivent en gardent l'histoire, lot par lot.

**Réaffirmation (lot L5, 2026-10-06)** : toutes les `GLORFINDEL_REASSERT_INTERVAL_S` (défaut 60 s, 0 = off ; jamais en dry-run ni read-only), le watch vérifie chaque isolation et blocage enregistrés (`glorfindel/reassert.py`). Règles **disparues** d'Azure (un `terraform apply` sur un NSG à règles en ligne, un retrait dans le portail) → reposées **une fois** + escalade `verification_failed` (l'heure d'isolation d'origine est gardée, `reasserted_at` noté) ; disparues **à nouveau** → escalade seule, Glorfindel ne se bat pas contre une suppression délibérée ou un pipeline. En `human_only`, jamais de repose : alerte seule. **Ce que dit la carte d'un blocage (RB1, #321, 29/10)** : reposé, le blocage est relu sur Azure — « reposé une fois » seulement s'il tient entier ; sinon la carte dit ce qui ne tient toujours pas (`partial`, une carte par épisode). Elle ne dit jamais « l'IP n'est plus bloquée » d'une IP que la règle de périmètre ou la quarantaine coupe encore (« l'IP reste bloquée sur … par la règle de périmètre … »), ni d'une carte dont la règle de périmètre est illisible (« on ne sait pas »), ni de cartes que la lecture n'a pas pu lire (nommées : « on ne sait pas si l'IP est encore bloquée sur <carte> ») ; une carte contournée est demandée au périmètre comme une carte dont les règles manquent, et une allow qu'un refus du client coupe déjà — tous ports, source comprise, l'attaquant nommé sans étiquette de service — ne contourne rien (I3P, #366). Un blocage fusionné (périmètre et VM dans une entrée) est reposé en entier : la règle de périmètre, puis celles de la VM (`docs/azure.md`, « Un blocage fusionné »). Les blocages qui tiennent un périmètre (fusionnés ou non) sont relus et reposés avant ceux des VM, quel que soit l'ordre des fichiers : un blocage de VM lu avant la paire de son sous-réseau disait « n'est plus bloquée » de cartes que la paire, reposée un instant plus tard dans la même passe, coupait de nouveau (L1Qr, #363). **En deux temps (L1Qs, #424, 03/11)** : deux entrées qui tiennent chacune un périmètre, sur deux sous-réseaux, une VM ayant une carte derrière chacun, s'attendent l'une l'autre — aucun ordre ne suffit. Premier temps (`glorfindel/reassert_perimeters.py`) : chaque paire de périmètre à reposer, de toutes les entrées, est reposée — décidé comme le second temps le déciderait (rien en `human_only`, déjà reposée, déjà dite et pas pire, tenue par un déblocage), marquée aussitôt (`reasserted_at`). Second temps : chaque entrée est lue et finie — les règles de sa VM, la relecture, la carte. Une entrée que le premier temps n'a pas pu lire (une lecture en échec) est faite au second, les périmètres toujours avant les VM. Une dérive qui va mieux que sa carte resserre sa référence dès la lecture, avant les écritures de l'entrée (pour une entrée écrite au premier temps, sur la lecture de celui-ci, reprise au second par le même prologue) : une écriture refusée (disque plein) ne la laisse plus à ce que disait la carte. Coût : une entrée de périmètre non écrite est lue deux fois par passe. Un watch coupé entre les deux temps laisse des paires reposées et marquées sans leur carte « reposé une fois » : la disparition suivante est dite « une deuxième fois », jamais tue. Une paire que le fournisseur a dite partielle, elle, est dite à la passe suivante (`partial_unsaid`, RW2). **Une carte acquittée (L1G, #461, 03/11)** : la vérification d'un blocage dit chacune de ses règles telle qu'elle l'a lue (`rules_seen` : ce qu'elle fait, ou absente), et la carte le garde. Une règle que la carte a lue sur Azure — retournée, ou visant une adresse que la carte réseau n'a plus, et dite « disparue » pour cela — puis supprimée est une règle de plus partie : dite de nouveau. De même d'une règle dite « disparue » parce que son NSG ne gouverne plus la carte — une quarantaine qui laisse passer l'IP (son accès d'investigation est celui de l'attaquant), ou un NSG que son propriétaire a ôté de la carte : la vérification lit ce NSG quand même, pour `rules_seen` seulement, son verdict inchangé (illisible, ses règles restent hors de `rules_seen`, jamais lues absentes). Supprimées après l'acquittement (un `terraform apply`), elles sont dites de nouveau ; avant, lues « pas pire » par leurs seuls noms, rien n'était dit tant que ce NSG restait hors de la carte, et la levée le lui rendait sans le blocage (L1N, #795, 13/11). Derrière une quarantaine qu'on ne sait pas juger (la configuration illisible : son accès d'investigation inconnu), ces règles sont lues aussi : parties ou altérées, le blocage est dit disparu, la carte laissée inconnue (« on ne sait pas si l'IP est encore bloquée »), jamais « plus bloquée » ; avant, la vérification disait « non vérifiable » seule et la disparition restait tue tant que la configuration restait illisible (L1Nd, #795, 16/11). Une règle que la carte a lue absente, écrite de nouveau sous notre nom (le blocage de périmètre d'une autre VM écrit la paire que toutes les entrées de cette IP et de ce sous-réseau nomment), clôt l'épisode d'une carte acquittée, comme un blocage écrit de nouveau (L1Q) : ce qui reste parti est reposé une fois, ou dit. La paire de périmètre aussi quand la carte l'avait lue sur Azure, retournée, et dite « disparue » pour cela (L1H, #483) : tenant de nouveau, elle a été écrite de nouveau — le blocage de périmètre d'une autre VM, le plus souvent —, l'épisode acquitté est fini. La paire seule : les règles propres à une VM, seul son blocage les écrit. Une règle de la VM remise à la main sans avoir été supprimée ne dit toujours rien (RB1) ; une paire retournée remise à la main se lit comme écrite de nouveau — une carte de plus plutôt qu'une disparition tue ; sous une carte en attente, ce qui revient resserre sa référence, comme avant. **Écrite puis repartie entre deux passes (L1W, #492, 04/11)** : la paire qu'une carte acquittée a dite partie (absente, ou là mais retournée), réécrite par le blocage de périmètre d'une autre VM, puis retirée de nouveau avant toute passe, se relit comme la carte l'avait lue — aucune lecture d'Azure ne montre l'écriture. Glorfindel note donc ses propres écritures de paire, avant chaque écriture (`~/.glorfindel/perimeter_writes.jsonl`, `glorfindel/response/pair_journal.py`) ; une paire notée après l'acquittement finit l'épisode, et ce qui reste parti est dit de nouveau, ou reposé une fois hors `human_only`. Une paire tenue à la carte, réécrite, ne finit rien ; une écriture avant l'acquittement non plus ; sous une carte en attente, rien de plus. Et une paire retournée relue à l'identique, tenant maintenant, n'est pas prise pour écrite de nouveau (`was != is_`). La lecture des NSG de quarantaine (ci-dessous) est dans `glorfindel/reassert_quarantine.py`. Un contournement (une allow d'un tiers avant le deny) n'est jamais réparé ni retiré : il est dit, une carte `bypassed` par isolation ou blocage et par changement, fermée quand le deny tient de nouveau (V-16, SEC4b — `docs/azure.md`, « La réaffirmation et les contournements ») ; une liste illisible ne déclenche rien ici. Derrière un contournement, ce qui manque est dit aussi (L1B, #355, comme I4C pour un blocage) : une isolation contournée dont les règles que l'état enregistre ont disparu d'un NSG qui gouverne leur carte (une ancienne paire contournée sur le NSG de la carte, la nôtre retirée de celui du sous-réseau) rend aussi `missing_rules` — reposée une fois, ou dite en `human_only`, comme toute disparition. Et l'inverse (L1C, #369) : une paire dont un sens a disparu, l'autre contourné par une allow avant lui, rend aussi `shadowed_by` à côté de ce qui manque (un blocage, une isolation) — la carte de dérive et celle du contournement, les deux ; un autre nom de la carte ne remplace un placement que s'il y refuse (sa paire, deux deny), jamais une règle retournée en allow. Un état local illisible est dit à chaque changement de la liste des fichiers illisibles, sur une carte `state_unreadable` (une fois, fermée quand tout se lit — `~/.glorfindel/state_alerts.json`) : la passe ne peut pas vérifier ce qu'il tient (SEC4b). **Ces cartes suivent la règle de L2Q (L2C, #343, 30/10)** : un contournement, un état illisible, les règles qu'un blocage a laissées (I4A) ne se taisent sur leur marque (`bypass_said`, `state_alerts.json`, `left_said`) que si leur carte attend, ou si la dernière carte de la ressource est la leur, fermée par un humain — les fermetures de Glorfindel portent une note. Une marque qu'on n'a pas pu écrire (disque plein) ne fait plus taire un changement qui revient ; un autre ensemble de règles laissées ferme l'ancienne carte au lieu d'y être fondu. Une disparition aussi (la relecture de L2C) : `drift_alerted_at` ne la fait taire que si la dernière carte de son alerte attend ou a été fermée par l'opérateur (les fermetures de `_alert` portent une note), et si le watch a vu l'épisode ouvert (sa marque écrite après sa carte), jamais fini depuis : acquittée, remise en place puis disparue de nouveau, elle est redite, même si la marque n'a pas pu s'effacer. **Quelle que soit la casse du nom de la VM (I3C, #436, 02/11)** : les ids de ces cartes (dérive, contournement, vérification qui échoue, règles laissées) s'écrivent en minuscules, et chaque recherche les lit sans casse (`reassert_cards.same_sid`) — une VM isolée ou bloquée de nouveau par son id en minuscules (le `_ResourceId` de Log Analytics) a un état qui la nomme ainsi ; la carte dite sous son nom canonique n'était ni fermée ni lue « déjà dite » : la disparition redite à chaque passe en `human_only`, reposée après avoir été dite hors de lui. Une carte en attente d'une version antérieure, sous le nom canonique, est retrouvée : fermée par l'alerte suivante, jamais orpheline. **Reprise bruyante** (décision de Jonathan, 30/10) : après un redémarrage du watch, chaque disparition acquittée et toujours là est redite une fois, sur une carte nouvelle, puis se tait ; hors `human_only`, une remise en place qui avait échoué est retentée une fois à ce passage (une écriture qui ferme, déjà permise par le mode, au plus une fois par redémarrage). Une écriture d'état refusée sur une VM n'arrête pas la passe : elle est dite (« état local non écrit », un échec affiché par le watch). Les isolations/blocages `partial` sont laissés à l'opérateur. Chaque alerte de réaffirmation remplace la précédente pour la même VM/IP (nouvelle carte, nouvelle notification) : la dédup du store fusionnait « disparues à nouveau » dans la carte « reposées une fois », texte inchangé, sans notification. **Une alerte par disparition** (`drift_alerted_at`, effacé quand l'isolation/le blocage est de nouveau en place) : en `human_only`, chaque cycle de 60 s recréait une carte et une notification, et défaisait les acquittements (validation du 06/10). Ce marqueur n'est écrit qu'**après** la carte (L1F, 27/10) : posé avant, un crash ou une carte qu'on n'a pas pu écrire entre les deux laissait « déjà alerté » sans carte, et chaque passe suivante se taisait sur un blocage disparu (trouvé par la machine à invariants, L1). Au pire, une carte redite à chaque passe tant que le marqueur ne peut pas s'écrire ; jamais le silence sur un blocage qu'on n'a pas pu reposer. **La carte remplacée se ferme dans l'écriture de sa remplaçante (L1A, #480, 03/11)** : une nouvelle alerte fermait d'abord la carte en attente, puis écrivait la sienne ; refusée (disque plein), il ne restait aucune carte, la marque d'avant lue « dit », et une passe qui ne pouvait pas vérifier le blocage (`unverified`) se taisait. `escalations.record(replaces=…)` ferme les cartes remplacées, avec leur note, dans la même écriture que la nouvelle : refusée, l'ancienne attend toujours, et la marque n'est pas posée. De même pour les cartes de contournement, de règles laissées, d'état illisible, de quarantaine et d'orphelines (`docs/design/preuves.md`, « L1A »). Limite connue : quand le blocage **est** reposé, `reasserted_at` est écrit avant la carte d'information « reposé une fois » — un crash entre les deux perd cette carte, pas la protection (le blocage est remis) ; l'ordre est gardé exprès, l'inverse ferait mentir la carte (« s'il disparaît encore, Glorfindel alertera sans le reposer ») sur la disparition suivante. Le journal d'activité cité ne garde que les écritures `Succeeded` d'autres identités que Glorfindel. **Un seul écrivain par VM (L12, 07/10)** : isoler, lever, bloquer, débloquer et `reset --from-azure` tiennent le verrou de la VM (`_vm_lock` : thread + flock `~/.glorfindel/locks/`, réentrant) — la console et la CLI sont d'autres processus ; la réaffirmation prend ce verrou et **relit l'état** avant d'agir (une levée en cours finit d'abord, puis l'état effacé dit qu'il n'y a rien à reposer). Levée et déblocage notent leur intention avant de toucher Azure (`releasing_at` / `unblocking_at`) : coupés au milieu, ils ne sont pas pris pour un retrait hors Glorfindel. Levée/déblocage partiels (`release_failed` / `unblock_failed`) laissés à l'opérateur — un déblocage échoué ou coupé, jusqu'à ce que l'IP soit bloquée de nouveau **en entier** : ce blocage le remplace, ses marques (`unblock_failed`, `unblocking_at`, `stale_alerted_at`) s'effacent et la passe le vérifie de nouveau (L1B, #355 ; avant, fusionné dans l'entrée, il gardait la marque et n'était plus jamais vérifié : ses règles disparues, rien n'était dit). Un blocage écrit de nouveau en partie la garde. Écrit en entier, il efface aussi la marque d'une disparition dite avant lui (`drift_alerted_at`, `drift_said`) et celle d'une remise (`reasserted_at`) : un nouveau blocage, un nouvel épisode, comme une nouvelle isolation (L1Q, #363 ; avant, la marque d'une carte acquittée faisait taire ce que l'entrée nomme encore et qu'Azure n'a plus — la règle de périmètre d'une entrée fusionnée, levée par le déblocage d'une voisine). Et une disparition dite, acquittée, qui va mieux sans finir (les règles de la VM remises, la paire de périmètre toujours absente) : à chaque passe qui va mieux que la carte, en attente ou acquittée, ce qui tient encore d'elle devient la référence, en mémoire, pour son épisode seulement ; les règles reparties sont redites (L1Q ; avant, « pas pire que la carte », elles se taisaient — et, la référence resserrée seulement après l'acquittement, une dérive allée mieux sous la carte en attente, puis acquittée, puis repartie avant la passe suivante se taisait pour tout l'épisode : seconde relecture). **Limite connue, voulue** : sous une carte en attente, une dérive qui va et vient refait une carte à chaque retour — une carte de trop plutôt qu'une disparition tue. Timeout des levées console : 600 s. La passe de réaffirmation tourne dans **son propre thread** (une réapplication coupe les sessions par Run Command, jusqu'à 300 s : elle bloquait la boucle principale — lecture des signaux, TTL, heartbeat) ; jamais deux passes à la fois. **NSG de quarantaine modifié, état perdu (I1F, 27/10)** : à chaque intervalle de la passe, **que l'état local soit vide ou non** (`reassert_pass` : les isolations et blocages enregistrés s'il y en a, puis les NSG de quarantaine, puis les règles orphelines — A3, ci-dessous), Glorfindel lit ses NSG de quarantaine (`find_altered_quarantines`, chacun par contenu comme `verify_isolation`, Q6). **Coût** : un listing des NSG de l'abonnement par passe (`network_security_groups.list_all`, paginé, lecture seule) — toujours tout l'abonnement : limité au groupe `isolation.quarantine_rg`, un NSG de quarantaine créé dans un autre groupe avant que le réglage change n'était plus lu (seconde relecture d'I1F). Un listing en échec (429, 403) ne ferme aucune carte. Un NSG modifié qui porte encore des cartes → **une** carte `quarantine_altered` par NSG et par changement (ressource : le NSG ; action `restore_quarantine_nsg`, rien d'exécutable ; sévérité haute, étapes suggérées ; hors décompte des décisions). Acquittée, elle ne revient pas tant que le changement est le même (`~/.glorfindel/quarantine_alerts.json`, le `drift_alerted_at` d'un NSG qu'aucun état ne nomme) ; un autre changement fait une autre carte. **Seul le dernier mot de l'opérateur fait taire un changement (L2Q, #331, 30/10)** : la dernière carte de ce NSG est celle de ce changement, fermée par un humain — les fermetures de Glorfindel portent une note (« a encore changé », ou entier, vide, disparu). Le fichier seul ne suffit pas : son écriture échoue (disque plein) après qu'un accès forensique a changé le diff, il garde l'ancien changement ; l'accès retiré, ou la configuration illisible qui le cache, le diff redevient l'ancien et était lu « déjà dit » — le NSG toujours vidé, sans carte. Il est redit. Limite : une carte fermée par Glorfindel avant L2Q n'a pas de note et se lit comme acquittée (le comportement d'avant, pour celle-là seulement). Elle se ferme d'elle-même quand le NSG est de nouveau entier, ne porte plus rien, ou n'existe plus — jamais sur un NSG lu « inconnu » (configuration illisible, nos deny intacts), ni quand la liste échoue. **Absent de la liste n'est pas disparu (I1S, 28/10, #231)** : la liste peut omettre un NSG sans erreur — rôle de Glorfindel retiré ou expiré (PIM) sur son groupe (hypothèse ci-dessous), notre tag `managed-by` retiré en plus de nos règles (`find_altered_quarantines` ne garde que les NSG nommés **et** tagués) — et une carte d'un autre abonnement (`AZURE_SUBSCRIPTION_ID` changé, `~/.glorfindel` partagé) n'y est jamais. Avant de fermer une carte (ou d'oublier un changement acquitté) dont le NSG manque à la liste, la passe le **relit par son ID** (`read_quarantine` : un `network_security_groups.get`, pour ces seules cartes — pas de `get` de chaque NSG à chaque passe) : introuvable (404) → fermée ; toute autre erreur (403, 429, réseau) → gardée ; trouvé → jugé sur son contenu, **tag présent ou non** ; d'un autre abonnement → gardée, jamais lue (les clients agissent dans l'abonnement du connecteur : son homonyme n'est pas lui) ; elle est écartée **avant** la relecture (`outside_subscription` du connecteur) et dite **une fois** par NSG dans le journal du watch (« quarantine NSG … is in subscription …, not the one Glorfindel reads … (said once) »), redite seulement si une nouvelle carte revient après la fermeture de la précédente — avant, la relecture la refusait et un avertissement s'écrivait à chaque passe, sans fin (ISU, #264). Un NSG refusé (403) de cet abonnement, lui, est dit à chaque passe : c'est un état réel. Ces messages nomment le NSG dans sa casse d'origine — un changement acquitté seul la retrouve dans ses cartes, au lieu de la clé en minuscules de `quarantine_alerts.json`. **Décision : un NSG retrouvé sans son tag garde sa carte** tant qu'il est modifié et porte des cartes. La carte a été levée sur ce NSG, nommé et tagué comme le nôtre, à cet ID ; retirer le tag en plus des règles, c'est la même main. Exiger en plus que ses cartes soient nommées par nos états manquerait le cas même d'I1F (l'état perdu). Un NSG sans tag n'est relu que parce qu'il a une carte : un autre changement y fait une autre carte ; une fois entier ou vide, sa carte se ferme et il n'est plus suivi (**limite connue** : la liste ne le dit plus nôtre ; un changement après coup n'est pas dit). Avant, la carte se fermait sur la simple absence, l'entrée de `quarantine_alerts.json` était effacée, et rien n'était dit jusqu'au retour des droits. Rien n'est écrit : sans état, rien ne dit quelle VM ni sous quel mode (I5) — toute isolation dans la région remet ses règles. Avant, une carte dont l'état et les tags étaient perdus restait dans une quarantaine que personne ne relisait : un deny passé en Udp la rouvrait en TCP, en silence ; et la passe ne lisait rien du tout quand l'état local était vide. **À mesurer au banc** : que la liste des NSG renvoie bien leurs `security_rules` complètes et leurs `network_interfaces` (vrai dans le faux Azure, pas mesuré), et son coût — un `list_all` par minute — sur un abonnement de taille réelle ; et, **hypothèse d'I1S, pas un fait** (avec Jonathan) : qu'un `list_all` des NSG **omette sans erreur** un NSG d'un groupe où l'identité n'a plus de droit (au lieu d'échouer en 403), et qu'un `get` de ce NSG renvoie alors 403 — le faux Azure le suppose (`unreadable`). La passe est `_watch_reassert_pass` (`glorfindel/watch/passes.py`, WCH1) ; une configuration illisible y est dite une fois, puis à nouveau seulement après être redevenue lisible.

**« Reposé une fois » finit son épisode (L1O, #507, 04/11)** : un blocage reposé finit l'épisode de sa disparition dans l'écriture de `reasserted_at`. L'épisode est clos en mémoire d'abord, quoi que fasse l'écriture, puis `drift_alerted_at` et `drift_said` sont ôtés dans cette même écriture. Reparti avant la passe suivante, tel que la repose l'avait lu, le blocage est dit « une deuxième fois » et n'est plus reposé, en `human_only` comme hors. Avant, la carte « reposé une fois », en attente ou acquittée, se lisait « déjà dit » et la passe se taisait, alors que cette carte promet « s'il disparaît encore, Glorfindel alertera sans le reposer ». Une repose qui ne tient pas en entier (`partial`) ouvre un nouvel épisode après sa carte, comme avant. Le premier temps (la paire de périmètre, L1Qs) finit l'épisode de même dans sa propre écriture de `reasserted_at` : le second temps sauté (son verrou pris), la paire repartie est dite. Sur Azure, l'adaptateur réécrivait déjà l'entrée à chaque blocage entier (`_save_block_state` ôte ces marques) ; la réaffirmation ne dépend plus de cet effet de bord (`docs/design/preuves.md`, « L1O »).

**La repose lit ce que répond le fournisseur (RW1, #513, 05/11)** : une écriture de blocage peut échouer sans lever. Sur AWS, `block_suspicious_ip` répond `failed` quand aucune entrée d'ACL n'est posable (aucun numéro libre avant l'allow qui laisse passer l'attaquant) et `partial` quand une entrée ne tient pas à sa relecture. Les deux temps de la repose (la paire, puis l'entrée) lisent ce statut. `failed` compte comme un échec levé : la carte dit « le reposer a échoué », avec la raison du fournisseur. `reasserted_at` n'est pas posé : la repose sera retentée, comme après une exception, une fois l'épisode fini ou après un redémarrage. `partial` compte comme une repose qui ne tient pas, quoi que dise la relecture : la carte dit « il ne tient pas en entier », jamais « reposé une fois ». Avant, `failed` faisait dire « ses règles réécrites une fois » de règles jamais écrites et la repose n'était plus retentée. `partial`, lui, marquait l'entrée sans carte : le second temps la sautait, tenue par sa propre marque. Une entrée que le fournisseur a notée `partial` n'est plus relue par aucune passe avant un nouveau blocage entier ou un déblocage, et sa carte le dit (« la réaffirmation ne le relit plus »), au lieu de promettre « Glorfindel alertera ». Sur Azure, rien de tel : un blocage par VM partiel lève (`PartialActionError`, déjà compté comme un échec), et le `blocked_partial` d'un blocage de périmètre (la règle posée, des cartes d'un autre sous-réseau hors de sa portée) reste jugé à la relecture. Ce `PartialActionError`, lui, reçoit la phrase « la réaffirmation ne le relit plus » : l'entrée est notée `partial` par Azure, comme sur AWS (RW2).

**La repose d'une isolation lit `verified` et `bypass` (RW2, #555, 05/11)** : sur AWS, `isolate_vm` répond `isolated` quoi que trouve sa relecture, avec `verified` à `False` (une ENI hors du groupe de quarantaine juste après l'échange, le groupe altéré) ou à `None` (illisible), et les ENI nommées dans `bypass`. Sur Azure, chaque deny est confirmé à son écriture et une carte laissée lève (`PartialActionError`, un échec), mais un deny écrit derrière une allow du client répond `isolated` aussi, avec `bypass` (`shadowed_by`) : c'était le trou côté Azure. Une isolation reposée qui ne tient pas compte comme une repose qui ne tient pas (`partial`) : la carte dit « reposée, elle ne tient pas en entier », avec les mots du fournisseur, et ne promet rien. Elle est reposée une fois quand même, comme un blocage : `reasserted_at` est posé (avec l'heure d'isolation d'origine : l'écriture d'Azure remet `isolated_at` à maintenant, et le TTL compterait depuis la repose), et `drift_alerted_at` l'est après la carte (une carte par épisode). Disparue de nouveau, elle est dite « une deuxième fois », escaladée seule, sans écriture : derrière une allow et un `apply` en boucle, Glorfindel n'écrit plus à chaque épisode. Avant, la carte disait « reposée une fois. Si elle disparaît encore, Glorfindel alertera » d'une isolation qui ne tenait pas. Une réponse qui ne dit rien (pas un dict) se lit comme avant. Une isolation que l'écriture laisse `partial` (`PartialActionError`) n'est plus relue par aucune passe avant une nouvelle isolation entière ou une levée, et sa carte « la reposer a échoué » le dit, comme pour un blocage. Ce que l'isolation tient une fois écrite est relu depuis RW3 (ci-dessous). **Les suites de RW1** : la paire qu'écrit le premier temps (L1Qs), que le fournisseur dit `partial`, porte une marque du premier temps, `partial_unsaid`, posée avant `reasserted_at`. Le second temps l'ôte une fois la carte dite (pas ôtée — un crash, un disque plein —, la carte est redite à la passe suivante : une carte de trop, jamais le silence). Sauté (verrou de la VM pris plus de 30 s, passe coupée entre les deux temps), il la trouve à la passe suivante : la marque `partial` du fournisseur ne tient plus l'entrée hors de la passe tant que sa carte n'est pas dite ; l'entrée est relue et sa carte écrite, sans rien écrire sur le cloud (le mode a pu changer depuis, `human_only` compris : la carte dit ce que la relecture trouve). Sa carte le dit (« sa règle de périmètre réécrite à la passe précédente »), et `reasserted_at` garde l'heure du premier temps. Avant, l'entrée restait hors de toute passe, sans carte. La marque n'est lue que si le fournisseur tient encore l'entrée `partial`, et un blocage écrit en entier l'efface (`_save_block_state`). La carte d'une écriture que le fournisseur a dite partielle, relue entière, dit « le fournisseur l'a dit partiel : à vérifier », plus « une écriture a échoué » : aucune n'a échoué. **Pour plus tard** : les cartes de la réaffirmation disent « avait disparu d'Azure » et « Azure le relit entier » sur AWS aussi ; des mots neutres (« du fournisseur ») restent à trouver, hors de RW2.

**La repose d'une isolation relit son effet (RW3, #575, 05/11)** : après `isolate_vm`, la repose relit l'isolation par `verify_isolation`, comme la repose d'un blocage relit le sien (A0). Sur Azure, chaque deny est confirmé à son écriture, jamais ce qui tient une fois tout écrit : une règle retirée entre deux écritures (un `apply` en boucle), une allow posée après le plan de l'écriture, une lecture refusée. La carte disait alors « reposée une fois. Si elle disparaît encore, Glorfindel alertera ». Désormais, une relecture qui ne tient pas (« relue, elle ne tient pas », avec les cartes sans isolation ou la raison) ou qu'on ne peut pas lire (`verified` à `None`, ou la lecture qui lève : « relue, elle n'est pas lisible ») compte comme une repose qui ne tient pas (`partial`). La carte le dit après les mots du fournisseur s'il y en a, et ne promet rien. La règle « une fois » de RW2 s'applique : `reasserted_at` posé (l'heure d'isolation d'origine gardée), `drift_alerted_at` après la carte ; disparue de nouveau, « une deuxième fois », escaladée seule, sans écriture. Un contournement que trouve la relecture a sa carte `bypassed` dès cette passe, comme pour un blocage (avant, à la passe suivante). Sur AWS, la relecture s'ajoute à celle que fait déjà l'adaptateur : une ENI remise dans ses groupes entre les deux est dite. **Coût, mesuré** (`tests/unit/test_reassert_reread.py`) : un `verify_isolation` de plus par repose, autant de lectures que la vérification qui la précède — sur Azure, 1 + 4 par carte pour une isolation par règles (la VM, puis pour chaque carte : la carte, son sous-réseau, son NSG, les règles du NSG), soit 5 pour une carte et 9 pour deux, et 2 sur AWS (l'instance, le groupe de quarantaine). Une passe où tout tient, ou en `human_only`, ne relit rien de plus. La passe d'une isolation par règles reposée sur une carte passe de 15 à 20 appels. Aucune écriture de plus : le journal des écritures du faux Azure, que lit la machine à invariants, est inchangé.

Sa règle … »). La carte « réaffirmation sautée » se ferme à la première passe qui relit la VM, même après un redémarrage, et quand la VM est levée ou débloquée ; jamais tant qu'elle reste sautée. Sa relecture : tant que la cause est une lecture refusée, la paire reste reportée (décision de Jonathan du 27/11, qui change la règle « essayée une fois » de la troisième relecture de RSM3) : une lecture par passe, rien d'écrit, sa carte mise à jour en place, la paire reposée une fois dès que la lecture passe ; la carte « sautée » n'est dite levée que d'après ce qui est enregistré, jamais sur un verrou qui lève une `OSError`.
